## 1. LLM (대규모 언어 모델)

### 1.1 LLM이란

LLM(Large Language Model)은 방대한 양의 텍스트로 학습해 사람처럼 언어를 이해하고 생성하는 인공지능 모델입니다. Claude, GPT, Gemini, Llama 등이 대표적입니다.

LLM의 본질은 **"다음에 올 토큰을 예측하는 모델"**입니다. "오늘 날씨가 정말"이라는 입력을 받으면 다음에 올 가능성이 높은 "좋다", "덥다" 같은 단어를 확률적으로 고르고, 이 과정을 반복해 문장을 완성합니다. 단순한 원리처럼 보이지만, 수천억 개 규모의 파라미터와 엄청난 양의 데이터로 학습하면서 요약, 번역, 추론, 코딩 같은 능력이 나타나게 됩니다.

대부분의 현대 LLM은 **트랜스포머(Transformer)** 구조를 기반으로 합니다. 트랜스포머의 핵심은 **어텐션(Attention)** 메커니즘으로, 문장 안의 각 단어가 다른 단어들과 얼마나 관련 있는지를 계산해 문맥을 파악합니다. 예를 들어 "그는 사과를 먹었다. 그것은 달았다"에서 "그것"이 "사과"를 가리킨다는 것을 어텐션을 통해 파악합니다.

### 1.2 LLM은 어떻게 만들어지는가

LLM은 일반적으로 다음 단계를 거쳐 만들어집니다.

| 단계 | 설명 | 결과 |
|------|------|------|
| **사전학습 (Pre-training)** | 인터넷 문서, 책, 코드 등 방대한 텍스트로 다음 토큰 예측을 학습 | 언어와 세상 지식을 갖춘 기반 모델 |
| **지시 튜닝 (Instruction Tuning)** | "질문 → 좋은 답변" 형태의 예시로 추가 학습 | 지시를 따르는 모델 |
| **선호 학습 (RLHF 등)** | 사람이나 AI의 평가를 바탕으로 더 유용하고 안전한 답변을 하도록 조정 | 대화형 어시스턴트 |

챗봇 개발자 입장에서 중요한 점은, 우리가 사용하는 모델은 **이미 학습이 끝난 상태**라는 것입니다. 학습 데이터에 없는 정보(회사 내부 문서, 학습 이후의 최신 정보)는 모델이 알지 못합니다. 모델이 학습한 데이터의 마지막 시점을 **지식 컷오프(Knowledge Cutoff)**라고 합니다.

### 1.3 토큰과 컨텍스트 윈도우

#### 토큰 (Token)

LLM은 텍스트를 글자나 단어 단위가 아니라 **토큰**이라는 단위로 처리합니다. 토큰은 단어의 일부, 단어 전체, 또는 문장부호일 수 있습니다.

- 영어는 대략 1토큰 ≈ 4글자 ≈ 0.75단어 정도입니다.
- 한국어는 모델의 토크나이저에 따라 다르지만 일반적으로 영어보다 같은 의미를 표현하는 데 더 많은 토큰이 필요한 경우가 많습니다.

토큰이 중요한 이유는 다음과 같습니다.

- **비용**: API 요금은 입력 토큰과 출력 토큰 수에 따라 부과됩니다.
- **속도**: 출력 토큰이 많을수록 응답이 느려집니다.
- **한계**: 한 번에 처리할 수 있는 토큰 수에 제한이 있습니다.

#### 컨텍스트 윈도우 (Context Window)

모델이 한 번의 요청에서 처리할 수 있는 최대 토큰 수입니다. 여기에는 **시스템 프롬프트 + 대화 기록 + 참고 문서 + 질문 + 답변**이 모두 포함됩니다.

```
┌─────────────────── 컨텍스트 윈도우 ───────────────────┐
│ 시스템 프롬프트 │ 이전 대화 기록 │ 검색된 문서 │ 질문 │ 답변 │
└──────────────────────────────────────────────────────┘
```

최신 모델들은 수십만 토큰 이상의 큰 컨텍스트 윈도우를 지원하지만, 컨텍스트가 길어질수록 비용이 늘고, 긴 입력의 중간 부분 정보를 놓치는 경향("Lost in the Middle" 현상)이 보고되기도 합니다. 따라서 **필요한 정보만 골라서 넣는 것**이 여전히 중요하며, 이것이 RAG가 필요한 이유 중 하나입니다.

### 1.4 LLM의 무상태성 (Stateless)

LLM API는 **이전 요청을 기억하지 않습니다.** 각 요청은 완전히 독립적으로 처리됩니다.

```
[요청 1] 사용자: 내 이름은 민수야
         AI: 안녕하세요 민수님!

[요청 2] 사용자: 내 이름이 뭐야?
         AI: 죄송하지만 모르겠습니다.   ← 이전 대화를 모름
```

챗봇이 대화를 기억하는 것처럼 보이게 하려면, 매 요청마다 **이전 대화 전체를 함께 보내야** 합니다.

```
[요청 2] 사용자: 내 이름은 민수야
         AI: 안녕하세요 민수님!
         사용자: 내 이름이 뭐야?          ← 이전 대화 + 새 질문을 함께 전송
         AI: 민수님이시죠!
```

이 때문에 대화가 길어질수록 매번 보내는 토큰이 늘어나고 비용도 커집니다. 이를 관리하는 방법은 다음과 같습니다.

- **최근 N개 메시지만 유지**: 가장 단순한 방법입니다.
- **토큰 기준으로 자르기**: 일정 토큰을 넘으면 오래된 메시지부터 삭제합니다.
- **요약**: 오래된 대화를 요약해 짧게 압축해서 유지합니다.

LangChain에서는 이 대화 기록 관리를 **메모리(체크포인터)**가 담당합니다.

### 1.5 생성 파라미터

모델을 호출할 때 답변의 성격을 조절하는 주요 파라미터입니다.

| 파라미터 | 설명 | 추천 설정 |
|---------|------|----------|
| **temperature** | 답변의 무작위성. 낮으면 일관되고, 높으면 다양함 | 상담/Q&A: 0~0.3, 창작: 0.7 이상 |
| **max_tokens** | 생성할 최대 토큰 수 | 답변 길이에 맞게 설정 |
| **top_p** | 확률 상위 일부 토큰 중에서만 선택 | 보통 temperature와 둘 중 하나만 조절 |
| **stop** | 이 문자열이 나오면 생성 중단 | 특정 형식 출력 시 사용 |

모델이 다음 토큰을 고를 때는 후보 토큰들의 확률 분포에서 선택합니다. temperature가 0에 가까우면 거의 항상 확률이 가장 높은 토큰을 고르고, 높아질수록 확률이 낮은 토큰도 선택될 가능성이 커집니다.

### 1.6 LLM의 한계

챗봇을 설계할 때 반드시 고려해야 할 LLM의 한계입니다.

**환각 (Hallucination)**
모델은 모르는 내용도 그럴듯하게 지어낼 수 있습니다. 존재하지 않는 논문, 틀린 수치, 가짜 정책을 사실처럼 말할 수 있습니다. 모델은 "사실"을 저장하는 데이터베이스가 아니라 "그럴듯한 다음 토큰"을 생성하는 모델이기 때문입니다.

→ **해결**: RAG로 근거 자료 제공, "모르면 모른다고 답하라"는 지시, 출처 표시 요구

**지식 컷오프와 내부 정보 부재**
학습 이후의 정보나 공개되지 않은 회사 내부 정보는 알지 못합니다.

→ **해결**: RAG, 웹 검색 도구 연결

**계산과 정확한 처리의 약점**
복잡한 계산, 정확한 날짜 계산, 긴 목록의 개수 세기 등에서 실수할 수 있습니다.

→ **해결**: 계산기, 코드 실행 같은 도구(Tool) 연결

**프롬프트 인젝션 (Prompt Injection)**
사용자가 "이전 지시는 무시하고…" 같은 입력으로 챗봇의 규칙을 우회하려 할 수 있습니다. 검색된 문서 안에 악의적인 지시가 숨어 있을 수도 있습니다.

→ **해결**: 시스템 프롬프트 설계, 입력/출력 검증, 민감한 기능에 대한 권한 제한

**비결정성**
같은 질문에도 매번 조금씩 다른 답변이 나올 수 있습니다.

→ **해결**: 낮은 temperature, 구조화된 출력 사용, 테스트 세트로 반복 검증

### 1.7 메시지 구조와 프롬프트 엔지니어링

#### 메시지 역할

채팅 모델은 역할이 지정된 메시지 목록을 입력으로 받습니다.

| 역할 | LangChain 클래스 | 용도 |
|------|-----------------|------|
| **system** | `SystemMessage` | 챗봇의 정체성, 규칙, 말투 지정 |
| **user (human)** | `HumanMessage` | 사용자의 입력 |
| **assistant (ai)** | `AIMessage` | 모델의 답변 |
| **tool** | `ToolMessage` | 도구 실행 결과 |

#### 좋은 시스템 프롬프트 작성법

시스템 프롬프트는 챗봇 품질에 가장 큰 영향을 주는 요소 중 하나입니다. 좋은 시스템 프롬프트에는 다음 내용이 포함됩니다.

1. **역할**: 챗봇이 누구인지 (예: "ABC 쇼핑몰의 고객 상담원")
2. **목적과 범위**: 무엇을 도와주고, 무엇은 다루지 않는지
3. **행동 규칙**: 모를 때의 대응, 금지 사항
4. **말투와 형식**: 존댓말 여부, 답변 길이, 형식
5. **예시**: 좋은 답변의 예시 (Few-shot)

```text
너는 ABC 쇼핑몰의 고객 상담 챗봇이야.

[역할]
- 주문, 배송, 교환/환불에 관한 고객 질문에 답변해.
- 쇼핑몰과 관련 없는 질문에는 정중하게 상담 범위를 안내해.

[규칙]
- 반드시 제공된 참고 자료에 근거해서만 답변해.
- 참고 자료에 없는 내용은 추측하지 말고 "상담원 연결"을 안내해.
- 개인정보(주민번호, 카드번호)는 절대 요청하지 마.

[말투]
- 친절한 존댓말을 사용하고, 3~5문장 이내로 간결하게 답해.
```

#### 주요 프롬프트 기법

- **Zero-shot**: 예시 없이 지시만 제공합니다.
- **Few-shot**: 입력-출력 예시 몇 개를 함께 제공해 원하는 형식과 스타일을 학습시킵니다.
- **Chain-of-Thought**: "단계별로 생각해봐"처럼 추론 과정을 거치게 해 복잡한 문제의 정확도를 높입니다.
- **구조화된 출력**: JSON 스키마 등을 지정해 정해진 형식으로 답하게 합니다.

## 2. RAG (검색 증강 생성)

### 2.1 RAG란

RAG(Retrieval-Augmented Generation, 검색 증강 생성)는 **LLM이 답변을 생성하기 전에 외부 지식 저장소에서 관련 정보를 검색해 프롬프트에 함께 넣어주는 기법**입니다.

비유하자면, 일반 LLM이 "기억에만 의존하는 클로즈드북 시험"이라면, RAG는 "관련 자료를 찾아보며 답하는 오픈북 시험"입니다.

```
[일반 LLM]
질문 ──────────────────────────────▶ LLM ──▶ 답변 (학습된 지식에만 의존)

[RAG]
질문 ──▶ 검색 ──▶ 관련 문서 ──┐
  └───────────────────────────┴──▶ LLM ──▶ 답변 (근거 문서 기반)
```

RAG의 장점은 다음과 같습니다.

- **최신/내부 정보 활용**: 모델을 다시 학습시키지 않고도 새로운 문서를 활용할 수 있습니다.
- **환각 감소**: 근거 자료를 제공하므로 지어낼 가능성이 줄어듭니다.
- **출처 제시**: 어떤 문서를 참고했는지 함께 보여줄 수 있어 신뢰도가 높아집니다.
- **쉬운 업데이트**: 문서가 바뀌면 벡터 DB만 갱신하면 됩니다.
- **접근 제어**: 사용자 권한에 따라 검색 가능한 문서를 제한할 수 있습니다.

### 2.2 RAG vs 파인튜닝

모델에게 새로운 지식을 주는 방법으로 파인튜닝도 있지만, 대부분의 문서 기반 챗봇에는 RAG가 더 적합합니다.

| 비교 항목 | RAG | 파인튜닝 |
|----------|-----|---------|
| **주된 용도** | 지식(사실, 문서 내용) 제공 | 말투, 형식, 특정 작업 방식 학습 |
| **정보 업데이트** | 문서만 교체하면 즉시 반영 | 재학습 필요 |
| **비용과 난이도** | 비교적 낮음 | 데이터 준비와 학습 비용 높음 |
| **출처 제시** | 가능 | 어려움 |
| **환각 제어** | 근거 문서로 제어 가능 | 여전히 발생 가능 |

일반적인 원칙은 **"지식은 RAG로, 행동 방식은 프롬프트(또는 파인튜닝)로"**입니다.

### 2.3 임베딩과 벡터 유사도

#### 임베딩 (Embedding)

임베딩은 텍스트를 **의미를 담은 숫자 벡터**로 변환하는 기술입니다. 임베딩 모델은 문장을 수백~수천 차원의 숫자 배열로 바꾸며, 의미가 비슷한 문장일수록 벡터 공간에서 가까운 위치에 놓입니다.

```
"환불하고 싶어요"         → [0.12, -0.45, 0.88, ...]  ┐
"돈 돌려받는 방법 알려줘"  → [0.15, -0.41, 0.85, ...]  ┘ 가까움 (의미 유사)

"오늘 날씨 어때?"         → [-0.73, 0.22, -0.10, ...]   멀리 떨어짐
```

이 덕분에 **키워드가 달라도 의미가 비슷하면 찾아낼 수 있는** 의미 기반 검색(Semantic Search)이 가능해집니다.

#### 유사도 측정

두 벡터가 얼마나 비슷한지는 주로 **코사인 유사도(Cosine Similarity)**로 측정합니다. 두 벡터 사이의 각도를 기준으로 하며, 1에 가까울수록 의미가 비슷하고 0에 가까울수록 관련이 없습니다. 그 밖에 유클리드 거리, 내적(Dot Product) 등도 사용됩니다.

#### 임베딩 모델 선택 시 고려사항

- **한국어 성능**: 한국어 문서라면 다국어를 잘 지원하는 모델을 선택해야 합니다.
- **차원 수**: 차원이 클수록 표현력이 좋을 수 있지만 저장 공간과 검색 비용이 늘어납니다.
- **비용과 배포 방식**: API 기반 모델(OpenAI 등)과 직접 실행 가능한 오픈소스 모델(HuggingFace 등) 중 선택합니다.
- **일관성**: 문서를 저장할 때와 질문을 검색할 때 **반드시 같은 임베딩 모델**을 사용해야 합니다.

#### 벡터 데이터베이스

임베딩 벡터를 저장하고 빠르게 유사도 검색을 해주는 데이터베이스입니다.

| 종류 | 특징 |
|------|------|
| **FAISS** | Meta에서 만든 로컬 라이브러리. 빠르고 가벼움 |
| **Chroma** | 설치가 쉬워 입문/프로토타입에 적합 |
| **Pinecone, Weaviate, Qdrant** | 서비스 운영에 적합한 전문 벡터 DB |
| **pgvector** | PostgreSQL 확장. 기존 DB와 통합하기 좋음 |

### 2.4 RAG 파이프라인 전체 흐름

RAG는 크게 **인덱싱(사전 준비)**과 **검색 및 생성(실시간 처리)** 두 단계로 나뉩니다.

```
━━━━━━━━━━━━━━━━━ ① 인덱싱 단계 (미리 1회 + 문서 변경 시) ━━━━━━━━━━━━━━━━━

 원본 문서        로드             분할            임베딩            저장
 (PDF, 웹,  ──▶ Document  ──▶  Text      ──▶  Embedding  ──▶  Vector
  DB 등)         Loader         Splitter        Model           Store

━━━━━━━━━━━━━━━━━ ② 검색 및 생성 단계 (질문이 올 때마다) ━━━━━━━━━━━━━━━━━

 사용자 질문 ──▶ 질문 임베딩 ──▶ 유사 문서 검색 ──▶ 프롬프트 구성 ──▶ LLM ──▶ 답변
                                (Retriever)      (질문 + 문서)
```

#### LangChain에서 각 단계를 담당하는 구성 요소

| 단계 | 구성 요소 | 예시 |
|------|----------|------|
| 로드 | Document Loader | `PyPDFLoader`, `WebBaseLoader`, `CSVLoader` |
| 분할 | Text Splitter | `RecursiveCharacterTextSplitter` |
| 임베딩 | Embeddings | `OpenAIEmbeddings`, `HuggingFaceEmbeddings` |
| 저장 | Vector Store | `Chroma`, `FAISS` |
| 검색 | Retriever | `vector_store.as_retriever()` |
| 생성 | Chat Model + Prompt | `init_chat_model(...)` |

LangChain에서 문서는 `Document` 객체로 다뤄지며, 본문(`page_content`)과 메타데이터(`metadata`: 파일명, 페이지 번호, 작성일 등)로 구성됩니다. 메타데이터는 출처 표시와 필터링에 활용되므로 잘 관리하는 것이 좋습니다.

### 2.5 청킹(Chunking) 전략

문서를 어떤 크기와 방식으로 나누느냐는 **RAG 품질에 가장 큰 영향을 주는 요소 중 하나**입니다.

#### 왜 나눠야 하는가

- 문서 전체를 하나의 벡터로 만들면 여러 주제가 섞여 의미가 흐려집니다.
- 질문과 관련된 부분만 정확히 찾아 넣어야 토큰을 아끼고 답변 정확도가 높아집니다.

#### 청크 크기의 트레이드오프

| 청크 크기 | 장점 | 단점 |
|----------|------|------|
| **작게** (예: 200~300자) | 검색이 정밀함 | 맥락이 끊겨 답변에 필요한 정보가 누락될 수 있음 |
| **크게** (예: 1500자 이상) | 맥락이 풍부함 | 관련 없는 내용이 섞여 검색 정확도 하락, 토큰 낭비 |

일반적으로 **500~1000자 정도에서 시작해 테스트하며 조정**하는 것을 권장합니다.

#### 오버랩 (Overlap)

청크 사이에 일부 내용을 겹치게 해서, 중요한 문장이 경계에서 잘려도 맥락이 유지되게 합니다. 보통 청크 크기의 10~20% 정도를 사용합니다.

```
청크 1: [■■■■■■■■■■□□]
청크 2:           [□□■■■■■■■■□□]
청크 3:                     [□□■■■■■■■■]
                 □ = 겹치는 부분 (overlap)
```

#### 분할 방식

- **고정 길이 분할**: 일정 글자 수로 자릅니다. 단순하지만 문장 중간이 잘릴 수 있습니다.
- **재귀적 분할** (`RecursiveCharacterTextSplitter`): 문단 → 줄바꿈 → 문장 → 단어 순으로 자연스러운 경계를 찾아 자릅니다. **가장 많이 쓰이는 기본 선택지**입니다.
- **구조 기반 분할**: 마크다운 제목, HTML 태그, 코드의 함수 단위 등 문서 구조를 따라 자릅니다.
- **의미 기반 분할 (Semantic Chunking)**: 문장 간 임베딩 유사도를 비교해 주제가 바뀌는 지점에서 자릅니다.

### 2.6 검색(Retrieval) 전략

기본적인 유사도 검색만으로도 동작하지만, 품질을 높이기 위한 다양한 전략이 있습니다.

**유사도 검색 (Similarity Search)**
질문과 가장 가까운 상위 k개 청크를 가져오는 기본 방식입니다. k는 보통 3~5개에서 시작합니다.

**MMR (Maximal Marginal Relevance)**
관련성이 높으면서도 서로 중복되지 않는 다양한 문서를 고르는 방식입니다. 비슷한 내용의 청크만 여러 개 검색되는 문제를 줄여줍니다.

**하이브리드 검색 (Hybrid Search)**
의미 기반 벡터 검색과 키워드 기반 검색(BM25)을 결합합니다. 벡터 검색은 의미를 잘 잡지만 제품 코드, 고유명사, 숫자 같은 정확한 키워드 매칭에 약할 수 있어, 두 방식을 함께 쓰면 보완이 됩니다.

**메타데이터 필터링**
"2025년 문서만", "인사팀 문서만"처럼 메타데이터 조건으로 검색 범위를 좁힙니다. 사용자 권한에 따른 접근 제어에도 활용됩니다.

**리랭킹 (Reranking)**
1차로 넉넉하게(예: 20개) 검색한 뒤, 더 정밀한 리랭커 모델로 질문과의 관련도를 다시 평가해 상위 몇 개만 남깁니다. 검색 정확도를 크게 높일 수 있는 방법입니다.

**쿼리 변환 (Query Transformation)**
사용자 질문을 검색에 더 적합한 형태로 바꿉니다.
- **쿼리 재작성**: 모호한 질문을 명확하게 고칩니다.
- **멀티 쿼리**: 하나의 질문을 여러 표현으로 바꿔 각각 검색합니다.
- **대화 맥락 반영**: "그거 환불돼?"처럼 이전 대화를 참조하는 질문을 "A상품 환불 가능 여부"처럼 독립적인 질문으로 바꿔 검색합니다. **대화형 RAG 챗봇에서 특히 중요합니다.**

### 2.7 생성 단계와 프롬프트 설계

검색된 문서를 프롬프트에 넣어 답변을 생성하는 단계입니다.

#### RAG 프롬프트 예시

```text
당신은 사내 규정 안내 챗봇입니다.
아래 [참고 자료]만을 근거로 질문에 답하세요.

규칙:
1. 참고 자료에 답이 없으면 "제공된 자료에서 해당 내용을 찾을 수 없습니다"라고 답하세요.
2. 추측하거나 자료에 없는 내용을 덧붙이지 마세요.
3. 답변 끝에 참고한 문서의 출처(문서명, 페이지)를 표시하세요.

[참고 자료]
{context}

[질문]
{question}
```

#### 설계 포인트

- **근거 제한**: "참고 자료에 근거해서만 답하라"는 지시로 환각을 줄입니다.
- **모를 때의 대응**: 답이 없을 때 어떻게 할지 명확히 지정합니다.
- **출처 표시**: 메타데이터를 함께 넣어 출처를 인용하게 하면 신뢰도가 올라갑니다.
- **문서 구분**: 여러 문서를 넣을 때 번호나 구분자로 명확히 나눠 모델이 혼동하지 않게 합니다.

#### 2-Step RAG vs 에이전트형 RAG

- **2-Step RAG**: 모든 질문에 대해 무조건 검색 → 생성을 수행합니다. 구조가 단순하고 예측 가능합니다.
- **에이전트형 RAG (Agentic RAG)**: 검색을 도구(Tool)로 제공하고, 모델이 필요할 때만 검색하거나 여러 번 검색하도록 합니다. "안녕하세요" 같은 인사에는 검색을 건너뛰고, 복잡한 질문에는 여러 번 검색할 수 있어 유연하지만, 동작을 예측하기는 조금 더 어렵습니다.

### 2.8 RAG 평가 방법

RAG는 **검색**과 **생성** 두 부분으로 나눠서 평가해야 어디에 문제가 있는지 파악할 수 있습니다.

| 평가 대상 | 평가 항목 | 질문 |
|----------|----------|------|
| **검색** | 문맥 정확도 (Context Precision) | 검색된 문서 중 실제로 관련 있는 비율은? |
| **검색** | 문맥 재현율 (Context Recall) | 답에 필요한 정보가 검색 결과에 모두 들어 있는가? |
| **생성** | 충실도 (Faithfulness) | 답변이 검색된 문서 내용에 근거하는가? (환각 여부) |
| **생성** | 답변 관련성 (Answer Relevance) | 답변이 질문에 실제로 답하고 있는가? |

#### 실전 평가 방법

1. 실제 예상 질문과 모범 답변으로 **테스트 세트**(최소 20~50개)를 만듭니다.
2. 설정(청크 크기, k값, 프롬프트 등)을 바꿀 때마다 테스트 세트로 결과를 비교합니다.
3. LangSmith 같은 도구로 각 질문에서 어떤 문서가 검색됐는지 추적합니다.
4. RAGAS 같은 평가 프레임워크나 LLM을 평가자로 활용(LLM-as-a-Judge)해 자동 평가할 수도 있습니다.

### 2.9 자주 겪는 문제와 해결법

| 증상 | 가능한 원인 | 해결 방법 |
|------|-----------|----------|
| 관련 문서가 검색되지 않음 | 청크가 너무 크거나 작음, 임베딩 모델의 한국어 성능 부족 | 청크 크기 조정, 다국어 임베딩 모델로 교체, 하이브리드 검색 |
| 정확한 키워드(제품명, 코드)를 못 찾음 | 벡터 검색의 키워드 매칭 약점 | BM25 하이브리드 검색 도입 |
| 비슷한 내용만 여러 개 검색됨 | 중복 문서 | MMR 검색, 중복 제거 |
| 문서는 맞는데 답변이 틀림 | 프롬프트 문제, 문서가 너무 많음 | 프롬프트 개선, k값 축소, 리랭킹 |
| 자료에 없는 내용을 지어냄 | 근거 제한 지시 부족 | "자료에 없으면 모른다고 답하라" 명시, temperature 낮추기 |
| 후속 질문("그건요?")에 엉뚱한 답 | 대화 맥락 없이 질문만으로 검색 | 쿼리 재작성으로 독립 질문 변환 |
| 표나 이미지 내용을 못 찾음 | 로더가 표/이미지를 제대로 추출 못함 | 표 전용 파서, OCR, 멀티모달 처리 |
| 오래된 정보로 답변 | 벡터 DB 미갱신 | 문서 변경 시 재인덱싱 파이프라인 구축 |

### 2.10 LangChain으로 구현하는 RAG 예시

아래는 PDF 문서를 기반으로 답변하는 에이전트형 RAG의 기본 구조입니다. (LangChain 1.x 기준이며, 패키지와 API는 공식 문서에서 최신 버전을 확인하세요.)

```bash
pip install langchain langchain-anthropic langchain-openai langchain-community langchain-text-splitters pypdf faiss-cpu python-dotenv
```

```python
from dotenv import load_dotenv
from langchain.chat_models import init_chat_model
from langchain.agents import create_agent
from langchain.tools import tool
from langchain_community.document_loaders import PyPDFLoader
from langchain_community.vectorstores import FAISS
from langchain_openai import OpenAIEmbeddings
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langgraph.checkpoint.memory import InMemorySaver

load_dotenv()

# ① 인덱싱: 로드 → 분할 → 임베딩 → 저장
docs = PyPDFLoader("company_policy.pdf").load()

splitter = RecursiveCharacterTextSplitter(chunk_size=800, chunk_overlap=100)
chunks = splitter.split_documents(docs)

embeddings = OpenAIEmbeddings(model="text-embedding-3-small")
vector_store = FAISS.from_documents(chunks, embeddings)
retriever = vector_store.as_retriever(search_kwargs={"k": 4})


# ② 검색 기능을 도구로 정의
@tool
def search_policy(query: str) -> str:
    """회사 규정 문서에서 질문과 관련된 내용을 검색합니다."""
    results = retriever.invoke(query)
    return "\n\n".join(
        f"[출처: {d.metadata.get('source')} p.{d.metadata.get('page', 0) + 1}]\n{d.page_content}"
        for d in results
    )


# ③ 에이전트 생성 (모델 + 도구 + 시스템 프롬프트 + 메모리)
model = init_chat_model("anthropic:claude-sonnet-4-5", temperature=0)

agent = create_agent(
    model=model,
    tools=[search_policy],
    system_prompt=(
        "너는 사내 규정 안내 챗봇이야. "
        "규정 관련 질문은 반드시 search_policy 도구로 검색한 결과에 근거해서 답해. "
        "검색 결과에 없는 내용은 추측하지 말고 모른다고 답하고, 답변 끝에 출처를 표시해."
    ),
    checkpointer=InMemorySaver(),
)

# ④ 대화 실행
config = {"configurable": {"thread_id": "user-1"}}
result = agent.invoke(
    {"messages": [{"role": "user", "content": "연차는 며칠까지 이월할 수 있어?"}]},
    config,
)
print(result["messages"][-1].content)
```

#### 실서비스로 확장할 때

- 인덱싱 코드는 별도 스크립트로 분리하고, 벡터 DB를 파일이나 서버에 저장해 매번 다시 만들지 않도록 합니다.
- `InMemorySaver` 대신 Postgres, SQLite 등 영구 저장소 기반 체크포인터를 사용합니다.
- 문서가 추가/수정될 때 자동으로 재인덱싱하는 파이프라인을 구축합니다.
- LangSmith를 연결해 검색 결과와 답변 품질을 지속적으로 모니터링합니다.

## 핵심 요약

- **LLM**은 다음 토큰을 예측하는 모델로, 기억이 없고(무상태), 컨텍스트 윈도우에 한계가 있으며, 모르는 내용을 지어낼 수 있다.
- 챗봇의 **대화 기억**은 이전 대화를 매번 함께 보내는 방식으로 구현한다.
- **RAG**는 질문과 관련된 문서를 검색해 프롬프트에 넣어줌으로써 최신/내부 정보를 활용하고 환각을 줄인다.
- RAG 품질은 **청킹 → 임베딩 → 검색 → 프롬프트** 각 단계의 설계에 달려 있으며, 검색과 생성을 나눠서 평가해야 문제를 정확히 찾을 수 있다.
