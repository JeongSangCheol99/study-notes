# Node.js 10.16.2 → 24.22.1 업그레이드 검토 및 테스트

## 1. 업그레이드 배경

현재 운영 서버에서는 Node.js v10.16.2를 사용하고 있음.

Node.js 10 버전은 이미 지원이 종료된 상태이며, 2026년 10월 Node.js 보안 업데이트 내용을 검토하면서 기존 운영 버전의 보안 및 유지보수 문제를 확인하게 됨.

보안 검토 자료에 정리된 주요 취약점은 다음과 같음.

| CVE | 취약점 내용 | 위험도 | 검토 자료상 해결 버전 |
|---|---|---|---|
| CVE-2026-105482 | DNS 호스트명 검증 우회 | 상 | 22.23.4 / 24.22.1 / 26.12.1 이상 |
| CVE-2026-105483 | TLS 인증서 검증 우회 | 상 | 24.22.1 / 26.12.1 이상 |
| CVE-2026-106069 | TLS 호스트명 검증 오류 | 상 | 22.23.4 / 24.22.1 / 26.12.1 이상 |
| CVE-2026-111497 | Brotli 메모리 손상 및 원격 코드 실행 | 치명적 | 22.23.4 / 24.22.1 / 26.12.1 이상 |

※ 위 취약점 및 해결 버전은 내부 보안 검토 자료를 기준으로 작성했으며, 실제 영향 여부는 각 취약점의 영향 버전 및 사용 조건을 별도로 확인해야 함.

특히 Brotli 관련 취약점은 Node.js 런타임에 압축/해제 기능이 포함되어 있는지와 실제 애플리케이션에서 해당 기능을 사용하는지 구분해서 확인할 필요가 있었음.

기존 운영 서버의 Node.js 10.16.2에서도 Brotli 압축 해제 기능이 제공되는 것을 확인했으나, 애플리케이션 소스와 주요 모듈에서 직접적인 Brotli 사용 코드는 발견되지 않았음.

다만 코드에서 직접 호출하지 않더라도 내부 라이브러리 사용 가능성까지 완전히 배제할 수는 없으므로 보안 업데이트가 필요한 상황으로 판단함.

이에 따라 기존 Node.js 10.16.2에서 **Node.js 24.22.1로 업그레이드하는 방향**으로 검토를 진행함.

## 2. 업그레이드 진행 방향

이번 작업의 목적은 Node.js 런타임 버전을 업그레이드하는 것이며, 기존 업무 소스코드의 수정이나 불필요한 라이브러리 업데이트는 진행하지 않는 것을 원칙으로 함.

운영 서버에서 바로 Node.js 버전을 교체하면 기존 서비스에 영향이 발생할 수 있기 때문에, 별도 로컬 테스트 환경에서 먼저 호환성을 확인하는 방식으로 진행함.

기본 진행 방향은 다음과 같음.

- 기존 운영 프로젝트와 설정 파일은 원본 상태 유지
- 운영 프로젝트를 별도 테스트 경로에 복사해 검증
- Node.js 24.22.1에서 기존 모듈 및 소스 동작 확인
- 호환되지 않는 라이브러리만 필요한 범위에서 별도 대응
- 기존 HTTPS 인증서 및 업무 소스코드 변경 없이 실행 가능한 방법 검토
- 실제 Oracle DB 연결 및 업무 기능은 운영 적용 시 최종 검증
- 운영 반영 전 백업 및 롤백 방안 확보

### 업그레이드 대상

| 항목 | 기존 환경 | 테스트 환경 |
|---|---|---|
| Node.js | 10.16.2 | 24.22.1 |
| npm | 6.9.0 | 11.19.1 |
| PM2 | 6.0.14 | 6.0.14 |
| node-oracledb | 3.1.2 | 26.0.0 |
| Oracle Instant Client | 11.2 | 19.26 |
| HTTPS 인증서 | 기존 PFX | 동일한 PFX 사용 |

Oracle Database 자체의 업그레이드는 이번 작업 범위에 포함하지 않음.

### 대상 프로젝트

**node-oracledb**

- Oracle Database와 연동하는 서비스
- Express 기반 HTTP/HTTPS 서버
- PM2 클러스터 방식으로 운영
- 운영 프로젝트 경로: `D:\node-oracledb`
- 테스트 경로: `D:\Node24OracleTest`

**TDCVADAuth**

- LDAP/AD 인증 서비스
- Express 및 ldapjs 기반
- PFX 인증서를 사용하는 HTTPS 서비스
- 프로젝트 경로: `D:\TDCVADAuth`

## 3. 로컬 테스트 환경 구성

운영 프로젝트를 직접 수정하지 않고 별도의 테스트 환경을 구성함.

로컬 PC에는 Node.js 24.22.1을 설치하고 기존 프로젝트의 소스 및 주요 의존성을 확인함.

Node.js 업그레이드에 직접적인 영향을 주는 모듈을 중심으로 테스트했으며, 기존 패키지의 취약점 전체를 수정하거나 최신 버전으로 일괄 업데이트하는 작업은 진행하지 않음.

### node-oracledb 테스트 환경

기존 업무 소스코드를 별도로 복사한 후 테스트용 npm 환경을 구성함.

테스트에 사용한 주요 모듈은 다음과 같음.

| 모듈 | 테스트 버전 |
|---|---|
| async | 1.5.2 |
| body-parser | 1.19.0 |
| cheerio | 1.0.0-rc.3 |
| cors | 2.8.5 |
| express | 4.17.1 |
| image-data-uri | 2.0.1 |
| request-ip | 2.1.3 |
| oracledb | 26.0.0 |

OracleDB를 제외한 주요 모듈은 기존 버전을 유지하는 방향으로 진행했으며, Node.js 24에서 모듈을 불러올 수 있는지 확인함.

그 결과 주요 모듈 로딩 및 소스 구문 검사는 정상적으로 통과함.

다만 모듈 로딩 성공만으로 기존 API의 모든 기능이 정상 동작한다고 판단할 수는 없으므로 실제 업무 기능 테스트는 별도로 필요함.

## 4. 업그레이드 과정에서 발생한 문제 및 해결 내용

### 4.1 OracleDB 드라이버 호환성 문제

**발생 현상**

기존 운영 환경에서 사용 중인 `oracledb@3.1.2`를 Node.js 24.22.1에서 로딩할 때 오류가 발생함.

```text
NJS-045: cannot load a node-oracledb binary
for Node.js 24.22.1 (win32 x64)
```

**원인**

기존 node-oracledb 3.1.2는 Node.js 10 환경에서 사용하던 버전으로, Node.js 24에서 필요한 네이티브 바이너리와 호환되지 않는 문제였음.

따라서 Node.js 실행 파일만 변경하고 기존 OracleDB 드라이버를 그대로 사용하는 방식은 어려운 것으로 확인함.

**대응 방법**

기존 업무 소스는 수정하지 않고 테스트 환경에서 다음과 같이 구성함.

- node-oracledb 26.0.0 설치
- Oracle Instant Client 19.26 사용
- 별도 `oracle-init.js` 파일 생성
- Node.js 실행 시 `--require` 옵션으로 Oracle Client 초기화
- Thick Mode를 사용하도록 설정

`oracle-init.js`에서는 다음과 같이 Oracle Client를 초기화함.

```javascript
const oracledb = require("oracledb");

oracledb.initOracleClient({
    libDir: "C:\\Oracle\\instantclient_19_26"
});
```

기존 `app.js`나 `server.js`에 초기화 코드를 추가하는 대신, 별도 파일을 실행 전에 로딩하는 방법을 사용함.

**테스트 결과**

```text
OracleDB: 26.0.0
Thick Mode: true
Oracle Client: 19.26.0.0.0
Node.js: v24.22.1
```

OracleDB 26.0.0 및 Oracle Client 19.26 Thick Mode 초기화에 성공함.

다만 실제 DB 연결 및 SQL 실행까지 검증한 것은 아니므로, 업무에서 사용하는 커넥션 풀과 쿼리가 정상 동작하는지는 추가 확인이 필요함.

### 4.2 기존 PFX 인증서 로딩 문제

**발생 현상**

Node.js 24 환경에서 기존 HTTPS 인증서(PFX)를 로딩할 때 다음 오류가 발생함.

```text
ERR_CRYPTO_UNSUPPORTED_OPERATION
Unsupported PKCS12 PFX data
```

**원인**

기존 PFX 파일에서 구형 암호화 방식이 사용되고 있는 것을 확인함.

확인된 주요 방식은 다음과 같음.

- SHA-1 기반 MAC
- TripleDES 기반 개인키 암호화
- RC2-40 기반 인증서 암호화

Node.js 24는 OpenSSL 3 계열을 사용하기 때문에, 기존 PFX에서 사용하던 일부 구형 암호화 알고리즘이 기본 설정에서 허용되지 않아 발생한 문제였음.

**대응 방법**

기존 PFX 파일을 재발급하거나 변환하지 않고 사용할 수 있는 방법을 우선 검토함.

Node.js 실행 시 다음 옵션을 적용해 테스트함.

```powershell
node --openssl-legacy-provider
```

**테스트 결과**

기존 PFX 파일 로딩에 성공했으며, 별도의 로컬 HTTPS 서버를 구성하여 실제 통신도 확인함.

```text
HTTPS Status: 200
Response: HTTPS TEST OK
PASS: HTTPS 통신 성공
```

또한 OracleDB 초기화 옵션과 PFX 호환 옵션을 동시에 적용한 상태에서도 초기화가 정상적으로 완료됨.

**고려사항**

`--openssl-legacy-provider`는 구형 암호화 알고리즘을 허용하는 옵션이므로 운영 환경에서 계속 사용할 경우 보안 검토가 필요함.

이번 테스트는 기존 인증서 파일을 변경하지 않는 조건에서 호환 가능성을 확인한 것이며, 장기적으로는 인증서의 암호화 방식 개선도 별도로 검토할 필요가 있음.

참고로 로컬 HTTPS 테스트에서는 인증서 신뢰 및 호스트명 검증을 비활성화했기 때문에, 실제 운영 HTTPS 인증서 검증까지 완료된 것은 아님.

### 4.3 Oracle DB 실제 연결 테스트 문제

OracleDB 드라이버 및 Oracle Client 초기화가 성공한 이후, 별도의 테스트 스크립트를 이용해 개발 DB 연결을 시도함.

이 과정에서 다음 오류가 발생함.

```text
ORA-12541: TNS:no listener
```

네트워크 연결을 확인한 결과, 대상 서버로의 Ping은 성공했으나 Oracle Listener 포트인 1521에 대한 TCP 연결은 실패함.

따라서 해당 오류는 Node.js 24와 OracleDB 드라이버의 호환성 문제라고 단정하기 어려우며, 개발 DB의 리스너 상태, 접속 정보 또는 네트워크 접근 정책을 확인할 필요가 있음.

DB 연결 테스트는 이후 실제 접속 가능한 환경에서 진행하는 것으로 정리함.

주의할 점은 기존 `app.js`가 로딩되는 과정에서 운영 DB 커넥션 풀 생성을 시도한다는 것임.

따라서 운영 DB에 영향을 주지 않으려면 로컬 테스트에서 기존 `server.js`를 바로 실행하지 않고, 독립적인 테스트 스크립트를 활용하는 것이 필요함.

## 5. PM2 클러스터 호환성 검증

기존 운영 서비스는 PM2 클러스터 방식으로 구동되고 있음.

Node.js 24에서 OracleDB 모듈이나 HTTPS 기능이 정상적으로 로딩되더라도 PM2를 통한 다중 프로세스 실행이 가능해야 하므로 별도의 클러스터 테스트를 진행함.

### 테스트 방법

실제 업무 서버 대신 간단한 HTTP 테스트 서버를 작성하고, PM2 클러스터 모드에서 2개 인스턴스를 실행함.

테스트 시 다음 Node.js 옵션을 함께 적용함.

```text
--openssl-legacy-provider
--require=D:\Node24OracleTest\oracle-init.js
```

### 확인 내용

- PM2 6.0.14 데몬 실행
- Node.js 24.22.1 환경에서 클러스터 2개 인스턴스 기동
- 두 인스턴스 모두 `online` 상태 확인
- PM2에서 Node.js 실행 옵션 전달 확인
- HTTP 요청 정상 처리
- OracleDB Thick Mode 초기화 확인
- PM2 재시작 후 서비스 정상 응답 확인
- 병렬 HTTP 요청 시 두 워커의 요청 처리 여부 확인

### 테스트 결과

PM2 클러스터 기동 및 재시작이 정상적으로 진행됨.

재시작 후 HTTP 요청 20회를 실행했을 때 모두 정상 응답했으며, 응답에서 Node.js 24.22.1과 OracleDB Thick Mode 활성화 상태를 확인함.

처음에는 요청이 하나의 PID에서만 처리되어 실제 분산 여부를 확인하기 어려웠음.

이에 따라 Windows PowerShell 환경에서 병렬 요청 테스트를 추가 진행함.

**병렬 요청 결과**

| 워커 PID | 처리 요청 수 |
|---|---:|
| 13824 | 29 |
| 31384 | 1 |
| 합계 | 30 |

두 워커 모두 실제 HTTP 요청을 처리하는 것을 확인함.

다만 요청이 29:1로 편중되었으므로 균등한 부하 분산이나 실제 운영 부하 환경에서의 성능까지 검증된 것은 아님.

이번 테스트를 통해 Node.js 24.22.1과 PM2 6.0.14를 함께 사용하여 클러스터를 실행할 수 있다는 점을 확인함.

## 6. TDCVADAuth 점검 결과

LDAP/AD 인증 서비스인 TDCVADAuth도 Node.js 업그레이드 대상에 포함되어 있어 별도로 점검함.

기존 서비스는 Express, cors, ldapjs를 사용하며 HTTPS 서버를 통해 인증 요청을 처리함.

### 진행한 점검

- 기존 JavaScript 파일 구문 검사
- Express 모듈 로딩 확인
- cors 모듈 로딩 확인
- ldapjs 모듈 로딩 확인
- LDAP 인증 처리 로직 확인
- 테스트용 모의 LDAP 응답을 이용한 인증 흐름 확인
- 기존 PFX 인증서의 Node.js 24 호환성 확인

### 인증 로직 테스트

| 테스트 항목 | 결과 |
|---|---|
| 정상 계정 인증 처리 | 통과 |
| 비밀번호 오류 처리 | 통과 |
| 계정 잠금 처리 | 통과 |
| JavaScript 구문 검사 | 통과 |
| 주요 모듈 로딩 | 통과 |
| 실제 AD 서버 연결 | 미검증 |
| 실제 HTTPS 인증 API 호출 | 미검증 |

모의 LDAP 응답을 이용한 테스트에서는 기존 인증 처리 로직이 정상적으로 동작하는 것을 확인함.

다만 실제 AD 서버에 연결하여 인증을 수행한 것은 아니므로, 운영 적용 전에 LDAP 연결 및 인증 API 동작을 별도로 확인해야 함.

## 7. 기존 업무 소스코드 변경 여부 확인

이번 업그레이드에서는 기존 업무 소스코드를 수정하지 않는 것을 중요하게 고려함.

이에 따라 원본 파일과 테스트 환경의 파일이 동일한지 SHA-256 해시값으로 비교함.

### 비교 대상

| 파일 | 원본과 테스트 파일 비교 |
|---|---|
| app.js | 동일 |
| server.js | 동일 |
| dbconfig.js | 동일 |

3개 파일 모두 SHA-256 해시값이 일치하는 것을 확인함.

즉, 주요 업무 소스코드를 직접 수정하지 않고도 OracleDB 초기화 및 HTTPS 호환성 테스트를 진행할 수 있었음.

다만 위 결과는 비교한 3개 파일에 대한 것으로, 프로젝트 전체 파일의 동일성을 검증한 것은 아님.

또한 이번 테스트에서 새로 작성한 `oracle-init.js` 및 PM2 테스트용 파일은 기존 업무 소스와 별도로 관리함.

## 8. 업그레이드 진행 시 고려사항

### 8.1 단순 Node.js 버전 교체만으로는 적용이 어려움

기존 OracleDB 드라이버 3.1.2는 Node.js 24에서 정상적으로 로딩되지 않았음.

따라서 Node.js 업그레이드와 함께 호환되는 OracleDB 드라이버 구성이 필요함.

다만 OracleDB 드라이버 교체는 실제 DB 연결 및 업무 SQL 동작에 영향을 줄 수 있으므로, 초기화 성공과 실제 업무 호환성을 구분해 확인해야 함.

### 8.2 기존 PFX 인증서 사용을 위한 실행 옵션 필요

기존 PFX 파일을 그대로 사용하려면 다음 옵션이 필요함.

```text
--openssl-legacy-provider
```

해당 옵션을 적용하면 로컬 환경에서 PFX 로딩 및 HTTPS 통신이 가능했음.

다만 보안 정책상 허용 가능한지 검토해야 하며, 운영 서버의 Node.js 실행 설정에 정확히 반영되어야 함.

### 8.3 Oracle Client 초기화 방식 확인 필요

기존 업무 소스 수정 없이 OracleDB Thick Mode를 사용하기 위해 다음과 같이 별도 초기화 파일을 사전 로딩함.

```text
--require=D:\Node24OracleTest\oracle-init.js
```

운영 적용 시에는 테스트 경로가 아닌 실제 운영 배포 경로를 기준으로 설정해야 함.

PM2 클러스터의 각 워커에서 OracleDB 초기화가 정상적으로 수행되는지도 확인해야 함.

또한 기존 `require('oracledb')`가 실제로 호환되는 드라이버를 참조하도록 Node.js 모듈 탐색 경로를 구성해야 함.

실행 옵션만 추가한다고 기존 OracleDB 3.1.2가 자동으로 26.0.0으로 교체되는 것은 아님.

### 8.4 PM2 운영 설정과 실제 실행 방식 확인 필요

테스트 환경에서는 PM2 클러스터 2개 인스턴스가 정상적으로 동작했음.

실제 운영 환경은 8개 워커로 구성되어 있으므로, 운영 적용 시에는 기존 프로세스 수와 실행 경로를 확인해야 함.

기존 `ecosystem.config.js`에서는 잘못된 따옴표로 인한 구문 오류가 발견되었으나, 실제 운영 PM2 프로세스가 해당 파일로 실행되고 있는지는 확인되지 않음.

따라서 운영에서 사용하지 않는 설정 파일이라면 이번 업그레이드 범위에 포함하지 않고, 실제 구동 방식을 기준으로 적용하는 것이 필요함.

### 8.5 실제 DB 및 업무 기능 검증 필요

현재까지는 OracleDB 드라이버 초기화와 PM2 클러스터 동작을 중심으로 검증함.

아래 항목은 아직 완료되지 않음.

- 실제 Oracle Database 접속
- 기존 커넥션 풀 생성 및 종료
- 세션 초기화 처리
- 주요 SQL 조회 및 업무 처리
- HTTP/HTTPS 업무 API 호출
- 실제 LDAP/AD 인증
- 운영 환경에서의 인증서 검증
- 운영 로그 및 성능 확인

따라서 지금까지의 테스트 결과만으로 운영 적용이 완료되었다고 판단할 수는 없음.
