# sendSms 메서드 코드 분석

## 1. 개요

`sendSms`는 SMS/MMS를 **직접 발송하지 않고**, 발송할 데이터를 DB에 등록하는 메서드이다.
실제 발송은 SMS 업체의 Agent 프로그램이 DB 발송 테이블을 조회하여 처리하는 **DB 연동형(Agent) 방식**으로 추정된다.

```
[웹 애플리케이션] → DB 발송 테이블 INSERT
                          ↓ (주기적 조회)
                [SMS 업체 Agent] → 통신사/중계 서버 → 수신자
```

> 실제 발송 테이블은 `FN_TB_SMS` 펑션 소스를 확인해야 정확히 알 수 있다.
> 펑션명의 `EM_MMT_FILE`로 보아 `EM_SMT_TRAN`(단문), `EM_MMT_TRAN`(장문/MMS) 계열 테이블을 사용할 가능성이 높다.

## 2. 처리 흐름

| 단계 | 처리 내용 | 호출 대상 |
|---|---|---|
| 1 | 첨부파일을 서버 디스크에 저장 (`APPEND_FILE_DIRECTORY/SMS/yyyyMM/`) | - |
| 2 | 첨부파일 정보 DB 등록 | `FN_TB_EM_MMT_FILE` |
| 3 | 수신자별 SMS 데이터 등록 | `FN_TB_SMS` |
| 4 | 업무코드(`smsBizCd`)가 10/20/30/40/60이면 고객 활동 이력 등록 | `FN_TB_CUST_ACTIVE` |
| 5 | 결과 반환 (성공 `00`, 실패 `99` + 메시지) | `jsonView` |

## 3. FN_TB_EM_MMT_FILE 펑션 분석

### 3.1 개요

MMS 첨부파일 정보를 `EM_MMT_FILE` 테이블에 등록하는 Oracle 펑션이다.
`sendSms`에서 물리 파일을 서버 디스크에 저장한 뒤, 파일 1건당 1회 호출된다.

| 항목 | 내용 |
|---|---|
| 작성자 / 작성일 | 김종훈 / 2016.4.4 |
| 대상 테이블 | `EM_MMT_FILE` |
| 처리 | INSERT만 수행 (수정/삭제 없음) |
| 반환값 | 성공 `'0'`, 실패 `'1'` |
| 오류 메시지 | `PV_RETURN_MSG`에 `SQLERRM` 저장 |

> `EM_MMT_FILE`은 SMS Agent가 MMS 첨부파일을 찾을 때 참조하는 테이블로 추정된다.
> 발송 테이블(`EM_MMT_TRAN` 등)에서 `ATTACH_FILE_GROUP_KEY`로 이 테이블을 연결하는 구조일 가능성이 높다.

### 3.2 파라미터

| 파라미터 | 용도 | Java에서 전달 여부 | 비고 |
|---|---|---|---|
| `PV_ATTACH_FILE_GROUP_KEY` | 첨부파일 그룹키 | O (`attachFileGroupKey`) | |
| `PV_ATTACH_FILE_GROUP_SEQ` | 그룹 순번 | X | NULL이면 `1` |
| `PV_ATTACH_FILE_SEQ` | 파일 순번 | X | NULL이면 `1` |
| `PV_ATTACH_FILE_SUBPATH` | 하위 경로 (`yyyyMM/`) | O (`attachFileSubpath`) | |
| `PV_ATTACH_FILE_NAME` | 저장 파일명 (`그룹키.확장자`) | O (`attachFileName`) | |
| `PV_CMD_TYPE` | 처리 구분 | O (`INSERT_MODE`) | **펑션 내부에서 미사용** |
| `PV_USER_ID` | 사용자 ID | 확인 필요 | **펑션 내부에서 미사용** |
| `PV_RETURN_MSG` | 오류 메시지 반환 | - | Java에서 `returnMsg`로 조회 |
| `PV_IS_COMMIT` | 펑션 내부 커밋 여부 | O (`false`) | `'1'`일 때만 COMMIT/ROLLBACK |

### 3.3 처리 흐름

```
EM_MMT_FILE INSERT (순번 NULL이면 1, 등록일 SYSDATE)
    ↓
PV_IS_COMMIT = '1' 이면 COMMIT
    ↓
RETURN '0'

[예외 발생 시]
PV_IS_COMMIT = '1' 이면 ROLLBACK
    ↓
PV_RETURN_MSG := SQLERRM
    ↓
RETURN '1'
```

### 3.4 문제점

#### 3.4.1 [심각] 파일 순번이 항상 1로 저장됨

- Java에서 `ATTACH_FILE_GROUP_SEQ`, `ATTACH_FILE_SEQ`를 전달하지 않아 **모든 파일이 순번 1로 저장**된다.
- 현재 Java 코드는 파일마다 그룹키를 새로 발급(`SELECT MAX`)하기 때문에 우연히 충돌이 나지 않는다.
- 그러나 첨부파일 여러 개를 하나의 그룹으로 묶도록 **그룹키를 한 번만 발급하게 수정하면**, 같은 그룹키에 순번 1인 파일이 여러 건 생겨 PK 위반 오류가 나거나 Agent가 파일을 구분하지 못한다.

**개선안**: 그룹키 발급 방식을 수정할 때 Java에서 파일 순번을 함께 전달한다.

```java
int fileSeq = 1;
for (...) {
    fileMap.put("attachFileGroupKey", attachFileGroupKey);
    fileMap.put("attachFileSeq",      String.valueOf(fileSeq++));
    fileMap.put("attachFileName",     fileName);
    fileMap.put("attachFileSubpath",  yyyyMM + "/");
}
```

> `EM_MMT_FILE`의 PK 구성과 Agent가 순번을 어떻게 사용하는지 먼저 확인해야 한다.

#### 3.4.2 [중간] 트랜잭션이 Java 쪽 커밋에 의존함

- Java에서 `PV_IS_COMMIT`을 `false`로 넘기므로 펑션 내부에서는 COMMIT하지 않는다. (`callDbFunction`이 `false`를 `'0'`으로 변환한다고 가정)
- 이 설계 자체는 여러 펑션(`FN_TB_EM_MMT_FILE`, `FN_TB_SMS`, `FN_TB_CUST_ACTIVE`)을 하나의 트랜잭션으로 묶기 위한 것으로 적절하다.
- 다만 Java 코드의 `getDataSource().getConnection().commit()`은 매번 새 커넥션을 가져오기 때문에 **실제 작업한 커넥션이 커밋/롤백되지 않는다.** 현재 데이터가 저장되는 것은 auto-commit 덕분일 가능성이 높으며, 이 경우 오류가 나도 앞서 등록된 첨부파일 정보는 롤백되지 않는다.

**개선안**: Java 쪽을 `@Transactional` 등으로 수정하고, 이 펑션이 같은 커넥션·트랜잭션 안에서 호출되는지 확인한다.

#### 3.4.3 [중간] 등록자 정보 미저장

- `PV_USER_ID`를 받지만 사용하지 않고, 테이블에 등록자 컬럼도 INSERT하지 않는다.
- 첨부파일을 누가 올렸는지 추적할 수 없다.

**개선안**: 테이블에 등록자 컬럼이 있다면 `PV_USER_ID`를 저장한다. 없다면 SMS 발송 데이터 쪽에서 등록자를 추적할 수 있는지 확인한다.

#### 3.4.4 [경미] 미사용 파라미터 및 IN OUT 선언

- `PV_CMD_TYPE`은 INSERT 외 분기가 없어 사용되지 않는다.
- 값을 돌려줄 필요가 없는 파라미터까지 모두 `IN OUT`으로 선언되어 있다.
- 공통 DAO(`callDbFunction`)의 호출 규약에 맞춘 것으로 보이므로, 변경 시 공통 호출 방식에 영향이 없는지 먼저 확인한다.

#### 3.4.5 [경미] 입력값 검증 없음

- 그룹키나 파일명이 NULL이어도 그대로 INSERT를 시도한다. 컬럼이 NOT NULL이면 `ORA-01400` 같은 DB 오류 메시지가 Java의 `ex.getMessage()`를 거쳐 화면까지 그대로 전달된다.

**개선안**: 필수값을 먼저 검사하고 의미 있는 메시지를 반환한다.

```sql
IF PV_ATTACH_FILE_GROUP_KEY IS NULL OR PV_ATTACH_FILE_NAME IS NULL THEN
    PV_RETURN_MSG := '첨부파일 정보가 올바르지 않습니다.';
    RETURN '1';
END IF;
```

### 3.5 Java 코드와의 연관 관계 정리

| 확인 항목 | 결과 |
|---|---|
| 오류 메시지 키 | 펑션이 `PV_RETURN_MSG`를 사용하므로 Java의 `returnMsg` 조회는 **정상**. SMS 등록 쪽은 `message` 키를 읽고 있어 `FN_TB_SMS`의 반환 형식 확인 필요 |
| 그룹키 발급 | 그룹키를 한 번만 발급하도록 수정할 경우 **파일 순번 전달이 반드시 함께 필요** (3.4.1) |
| 트랜잭션 | 펑션은 커밋하지 않으므로 Java 쪽 트랜잭션 수정이 필수 (3.4.2) |
| 파일 경로 | 하위 경로(`yyyyMM/`)만 저장하므로, Agent가 기본 경로(`APPEND_FILE_DIRECTORY`)를 알고 있어야 함 |

### 3.6 추가 확인 필요 사항

- [ ] `EM_MMT_FILE` 테이블의 PK 구성 및 NOT NULL 컬럼

- [ ] Agent 서버가 웹 서버의 첨부파일 경로에 접근 가능한지 (공유 스토리지 여부)
- [ ] `callDbFunction`이 `false`를 `PV_IS_COMMIT`에 어떤 값으로 전달하는지
